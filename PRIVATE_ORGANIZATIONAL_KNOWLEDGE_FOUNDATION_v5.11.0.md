# Private Organizational Knowledge Foundation — Library v5.11.0

## Purpose

Library v5.11.0 establishes a physically separate private knowledge plane for organizational research and internal knowledge. It does not repurpose the public `library_records` table or add private rows to public Library discovery.

## Private knowledge model

The v2.1.0 backend adds dedicated PostgreSQL tables for:

- organizations;
- organization-scoped sources;
- private records;
- private record version lineage;
- private ingest events; and
- privacy-minimized private access events.

Every private record has a stable organization-scoped record identity, source ownership/provenance, content hash, revision, access level, optional access scopes, project/department context, and retention label.

## Access boundary

Private data routes are POST-only and require the existing signed Sustainable Catalyst Library server credential. Organization identity and the authenticated actor packet are generated by the server-side WordPress proxy. The browser never receives the backend API key.

Access levels:

- `organization` — readable by an authenticated organization member admitted by WordPress;
- `restricted` — requires at least one matching actor scope;
- `project` — requires explicit access scope(s) and a project key.

Default actor scopes contain the current WordPress user ID and WordPress roles. Integrations can add project or custom scopes with the `sc_library_private_knowledge_actor_scopes` filter.

## Public/private separation

Public Library search and discovery remain on the existing public tables. v5.11.0 does not modify the public query module to read private tables. The private module is not added to the public Research Network Console or homepage source registry.

Cross-organization search and cross-organization identity consolidation are prohibited by design.

## Ingestion boundary

The private backend accepts normalized extracted-text packets and records original format metadata such as PDF, DOCX, TXT, Markdown, CSV, or JSON. v5.11.0 does not claim a new binary parser. Existing Library conversion/OCR/document-processing paths or future connectors can extract content and submit normalized packets.

The WordPress REST ingest proxy requires `upload_files` and accepts a normalized source packet plus bounded records.

## Version lineage

A deterministic content hash is computed from stable record content/metadata. Reingesting an unchanged record does not create a new revision. A changed record increments the revision and stores a private version snapshot.

## Audit boundary

Private ingest, search, read, version-history, and handoff operations create access events. Search audit events store a deterministic request fingerprint and result counts; they do not persist the raw search query in the audit event.

## Cross-product handoffs

v5.11.0 defines controlled handoff packets for:

- Research Librarian — bounded private context;
- Workspace — private record reference plus bounded context; and
- Lab — private analysis reference only for data-like records carrying explicit `analysis_allowed=true` metadata.

Every packet states that organization scope and access scopes must be preserved and that the handoff does not publish the record. Lab eligibility never infers permission from file type alone.

## WordPress surface

Shortcode:

`[sc_private_organizational_knowledge]`

The surface is available only to authorized signed-in users and supports private search, record detail, version lineage, and bounded handoff inspection.

Administrator settings:

- Organization key
- Organization name

The organization key is a stable tenant identifier and should not be changed casually after private data has been ingested.
